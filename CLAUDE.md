# jql

A JSON Query Language CLI. Cargo workspace, edition 2024, MSRV 1.88 (`rust-version` in the root
`Cargo.toml` — keep it at the true minimum, not the latest release).

- `crates/jql` — the binary. Argument parsing, output formatting, stdin/file/stream reading.
- `crates/jql-parser` — query text to `Vec<Token>`. No JSON knowledge.
- `crates/jql-runner` — evaluation. Two evaluators, see below.
- `fuzz/` — libFuzzer targets. `assets/` — the benchmark fixture.

## The two evaluators

`jql-runner` evaluates a query twice over, and which one runs is a performance decision only —
they must agree on every input, byte for byte, including which error comes back.

- `runner.rs` + `array.rs` + `object.rs` — the original `serde_json::Value` evaluator. **Treat it
  as frozen.** It is the published library API, the fallback for everything the tape declines, and
  the oracle both the parity tests and the fuzzer compare against. Change it only to fix a bug in
  it, never to accommodate the tape.
- `lazy.rs` — evaluates against a simd-json tape and materializes only what a query selects. This
  is what the binary calls. It hands anything it cannot do identically back to the runner:
  the flatten operator, nested pipes, input the tape builder rejects (nesting past simd-json's
  1024, more than one document, malformed), and numbers the two parsers disagree on.

Any change to `lazy.rs` needs a parity test in `crates/jql-runner/tests/parity.rs` and a clean
fuzz run. `assert_parity` compares serialized output so key order counts; error cases are compared
by value.

### Where the two parsers genuinely differ

Known and handled — read `numbers_may_diverge` and `outcome_may_diverge` before touching this:

- `-0` — serde_json gives the float `-0.0`, simd-json the integer `0`.
- a fractional literal with 16+ significant digits — the last bit can round differently.
- scientific notation — **an accepted departure**: literals can come back up to two ULP apart,
  because telling a number's exponent from an `e` inside a string needs a quote-aware scan. The
  tape is the correctly rounded side: measured over 300k random literals, every one of the 67,604
  that diverged had serde_json wrong and the tape right, so the fallback is the less accurate of
  the two. `scientific_notation_is_correctly_rounded_on_the_tape` pins the tape to Rust's own
  parse and bounds the oracle at two ULP; the README documents it.
- duplicate keys — serde_json keeps the last, the tape keeps every entry.
- integers past `u64` — the tape build fails, which sends the input to the runner.

The tape is given up per outcome, not per input: the hazards are looked for in what a query
returns, so a `-0` elsewhere in the document costs nothing. A lens comparing numbers decides the
*selection* rather than a returned value, so those queries keep the up-front scan.

## Commands

```sh
just test                  # cargo nextest run
cargo nextest run --workspace
cargo +nightly fmt --all   # rustfmt.toml uses nightly-only options
cargo clippy --all-targets --all-features -- -D warnings
just fuzz-lazy             # the dual-evaluator target, needs nightly + cargo-fuzz
./performance.sh           # hyperfine vs jq; needs jq and hyperfine, writes PERFORMANCE.md
```

Gates before handing over a commit: `fmt --check`, clippy clean on stable **and** MSRV
(`cargo +1.88.0`), the whole test suite, and for anything touching `lazy.rs`, the fuzzer.

## Conventions

- No comments that restate the code. A comment earns its place by recording *why* — a measurement,
  a parser quirk, an invariant a future change could break. Never add one without asking.
- Errors: no `unwrap`/`expect` in new code. The existing `unwrap`s in the frozen runner are
  guarded by a preceding type check and say so.
- `unsafe_code` is denied workspace-wide.
- Public items need docs (`missing_docs` is on) and both error enums are `#[non_exhaustive]`.
- Performance claims come with a measurement. `hyperfine -N` does not run a shell, so a command
  with a pipe measured under `-N` times the first process only — use shell mode for pipes.
- `PERFORMANCE.md` is generated by the release workflow, never edited by hand. The workflow
  benchmarks the *published* crate, so numbers land one release after a change.
